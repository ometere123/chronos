## LIVE-TESTING UPDATE — 2026-08-02 (real testnet click-testing, not just typecheck/build)

Actually clicked through the app end-to-end for the first time (Privy email-OTP login, create
vault, claim, early withdrawal) against real Base Sepolia / Arc testnet, funded by the user's own
wallet. Found and fixed 3 real bugs, all variants of the same root cause: **Arc/Base Sepolia
testnet RPC endpoints are genuinely flaky right now** (repeated "could not coalesce error" and
"request timeout" errors), and the code wasn't tolerant of that.

1. `frontend/lib/evm.ts` `waitForTransactionReceipt()` aborted the whole wait on a single transient
   RPC error during polling, even though the tx had already broadcast successfully. Fixed: retries
   transient errors, only a real timeout is fatal now.
2. `backend/src/services/arcSettlementService.js` had NO retry protection on any plain RPC read
   (`getTransaction`, `getTransactionReceipt`, `.getVault()`) - only sends were retried. Added a
   `readWithRetry()` helper (bumped to 6 attempts specifically for the flexible-withdrawal
   verification path, which proved the flakiest) and broadened the retryable-error patterns to
   include generic timeouts, not just the nonce/txpool-specific ones.
3. `backend/src/routes/vaults.js`'s `/claim` route: the independent `eventListenerService` can mark
   a vault CLAIMED (from the direct Arc `claimVault()` event) before the same request's own
   bridge-back-leg gets recorded - discovered live when a real, successful CCTP bridge-back-to-
   source-chain transaction got silently dropped/untracked because the route just 400'd on
   "vault already claimed" instead of still recording the bridge-back leg. Fixed: it now records
   the late-arriving bridge-back leg instead of dropping it.

**Known residual issue, not fully fixed:** during testing, two flexible-vault early-withdrawal
attempts succeeded on-chain (vault balance visibly dropped from $1.00 to $0.20 on the contract)
but the backend's `/withdraw` route 500'd both times on the verification read (before fix #2
above landed / before the retry budget was large enough), so the app's own "Early Withdrawn" and
"Penalties" stats never updated - they still read $0.00 for a vault where a real early withdrawal
definitely happened. Funds were never at risk (all on-chain), but the DB-side bookkeeping for
early withdrawals is unreliable under RPC flakiness. The retry-budget bump (fix #2) should reduce
how often this happens going forward, but there's no idempotency/replay safety net if verification
fails outright after several retries - worth a proper fix (e.g. don't gate the DB update on a
live RPC read succeeding synchronously in the request; or add a dedup table keyed on
`withdrawTxHash` so retries are cheap and safe) before relying on these stats for anything real.

### CRITICAL FINDING (RESOLVED) — duplicate on-chain vault settlement, real under-collateralization

While testing Smart Split vaults, hit a genuine solvency bug, fully traced and fixed:

1. The live database was missing the `is_split`/`savings_bps`/etc. columns (present in
   `schema.sql`, never migrated onto this DB — same class of gap as the streaming-vault columns
   found earlier this session). Applied both migrations live.
2. Before that fix landed, a split-vault creation succeeded **fully on-chain**
   (`settleSplitVault` → `depositFromBridgeSplit`) but then crashed on the DB insert
   (`column "is_split" does not exist`), so no vault record was ever saved.
3. Using "Recover a submitted burn" with the same burn tx hash re-ran the **entire** creation
   flow from scratch — including a second on-chain settlement — because the only dedup check
   (`buildExistingCreateResponse`) only looks at the database, and step 2 never wrote anything
   there to find.
4. Result: two separate on-chain vaults were created, each claiming 1 USDC of liability, backed
   by only one real 1 USDC CCTP-bridged deposit. Confirmed live via
   `GET /api/proof-of-reserves/verify`: `fullyReserved: false`, liabilities exceeding contract
   balance by exactly the duplicated amount.

**Fix (implemented and verified working):** added a new `vault_creation_settlements` table
(deliberately no FK to `vaults`) that records the on-chain settlement result — on-chain vault ID,
settlement tx hash, and all params needed to finish the DB write — **immediately after** each
`settleVault`/`settleSplitVault`/`settleStreamingVault`/`settleVaultAdvanced` call succeeds,
before the fragile DB insert. `buildExistingCreateResponse` now checks this table first: if a
settlement succeeded but was never persisted, it **completes the interrupted DB write** using the
already-known on-chain vault ID instead of re-running settlement. Verified live by creating a
fresh Streaming vault end-to-end through the new code path — succeeded cleanly in one pass.

**Reconciliation of the actual damage:** the orphaned duplicate vault's ~1 USDC shortfall was real
and pre-existing (this fix prevents recurrence, it doesn't retroactively undo past damage). Fixed
by calling `arcSettlementService.ensureTimeLockVaultReserve('4.0')` directly (topping up
TimeLockVault's balance from the relayer's own testnet USDC to cover the gap). Confirmed
`fullyReserved: true` afterward. The orphaned on-chain vault itself (`0xb2d7ad2d...`) still has no
backend DB record and is invisible to the app's UI, but is now fully collateralized — no user-facing
risk remains. If it matters for accounting, it can be manually inserted into the `vaults` table
using the on-chain data (owner, amount=1, unlockAt, `created_on_chain_tx`) at some point, but
isn't urgent.

## Key facts an agent picking this up needs to know

- **Deployed contracts**: all on Arc Testnet, addresses in root `.env.local` (gitignored, NOT in
  git). Has been redeployed 3 times today in EARLIER sessions (not today) as contracts changed -
  `.env.local`'s values are always the current source of truth.
- **`backend/.env` vs root `.env.local`**: `backend/src/config/env.js` loads `backend/.env` FIRST,
  then root `.env`/`.env.local` with `override:false` - meaning if the SAME key exists in both,
  `backend/.env`'s value wins even if stale. This bit us once already today (documented above).
  Don't add short-name duplicate keys to `backend/.env` - root `.env.local` is the single source
  of truth for contract addresses now.
- **`frontend/.env` is separate from root `.env.local`** - Next.js does NOT read the root-level
  `.env.local`, only files inside `frontend/`. Any `NEXT_PUBLIC_*` var needed by the frontend must
  be duplicated into `frontend/.env` (or `frontend/.env.local`). This bit us today too - the
  Privy App ID had to be added to both places.
- **Turbopack is broken in this sandboxed dev environment** (`next dev` defaults to it in Next
  16, panics with "Next.js package not found"). Use `npm run dev:webpack` (a script added
  earlier today, wraps `next dev --webpack`) instead. `.claude/launch.json` already has both
  `backend` and `frontend` configs pointing at the right commands.

- **On Windows, never run two `npm install` commands concurrently in the same directory** - this
